# Neural Network-Based Fault Injection Detection on STM32

A research platform for acquiring and analyzing electrical traces from a microcontroller subjected to voltage glitches, with the aim of developing an embedded neural network-based protection mechanism. The dataset distinguishes between **induced** events, generated by the attack circuit, and **self-induced** events, recorded without arming the attacker.

The system comprises three STM32 firmware projects, a Python measurement station, and tools for dataset preparation and neural network training. The STM32N6 is initially used for data acquisition; the resulting dataset supports the development of an attack detection model intended for deployment on the same platform.

## Architecture

| Project | Board | Role |
| --- | --- | --- |
| [`AdvancedFaultVictim`](AdvancedFaultVictim/) | NUCLEO-F401RE, STM32F4 | Victim: executes the workload and generates synchronization signals. |
| [`AdvancedFaultAttacker`](AdvancedFaultAttacker/) | NUCLEO-F401RE, STM32F4 | Attacker: receives a trigger and drives the external glitch injection circuit. |
| [`TheBodyguard`](TheBodyguard/) | NUCLEO-N657X0-Q, STM32N6 | Trace acquisition; target platform for integration of the neural network-based protection mechanism. |
| [`FaultMeasureStation`](FaultMeasureStation/) | PC and R&S RTB2000 oscilloscope | Board orchestration, acquisition, characterization, and filtering. |

The measurement station arms the oscilloscope and, for induced-event measurements, the attacker; it then initiates Bodyguard acquisition. The victim executes the workload, and its trigger synchronizes the attacker timer. The external circuit injects the glitch while Bodyguard and the oscilloscope record traces associated with the same trial.

### Victim: AES Workload

The F4 victim can execute an arbitrary workload. In this project, the workload consists of **AES-128-CBC** encryption of a 64-byte plaintext without padding.

The [victim firmware](AdvancedFaultVictim/Core/Src/main.c) contains three randomly generated key–plaintext pairs stored as constants. Each test set also includes the corresponding initialization vector (IV) and expected ciphertext:

- `key1`, `plaintext1`, `IV1`, `expectedCiphertext1`;
- `key2`, `plaintext2`, `IV2`, `expectedCiphertext2`;
- `key3`, `plaintext3`, `IV3`, `expectedCiphertext3`.

The test set is selected before compilation:

```c
#define AES_TEST_SET 1  /* 1, 2, or 3 */
```

The values remain fixed across executions to ensure reproducible experimental conditions. The victim activity signal is driven high at the start of the operation and low upon completion; its temporal behavior is also used to distinguish normal completion from a reset.

### Attacker: Glitch Generation

The [attacker firmware](AdvancedFaultAttacker/Core/Src/main.c) configures **TIM1 in One Pulse Mode**:

- **PA9 / TIM1_CH2:** trigger input from the victim;
- **PA8 / TIM1_CH1:** output to the attack circuit;
- **CCR1:** delay between the trigger and the pulse;
- **ARR and CCR1:** control pulse duration.

The measurement station arms the attacker via UART. In the current configuration, the pulse duration is approximately **1 µs**, and the firmware varies the delay. The timer controls pulse duration and timing; the voltage glitch depth depends on the external circuit and its settings, including the control resistor. The actual voltage level is verified using digital storage oscilloscope (DSO) acquisitions.

### Bodyguard: From Dataset Acquisition to Embedded Protection

The N6 acquires signals through two ADCs and transfers the buffers to the measurement station. This initial phase provides a labeled dataset for investigating the distinction between induced and self-induced events.

The [`TheBodyguard/NetworkTraining`](TheBodyguard/NetworkTraining/) directory contains tools for data processing, analysis, training, and model conversion. The next project phase is to integrate the network into the N6 to implement protection based on neural inference. Dataset acquisition and validation of the protection mechanism are distinct phases of the work.

## Measurement Station

| Script | Function |
| --- | --- |
| [`acquire.py`](FaultMeasureStation/acquire.py) | Orchestrates the boards and DSO; saves ADC and oscilloscope traces with a shared Run ID. |
| [`characterize.py`](FaultMeasureStation/characterize.py) | Characterizes the interval between the voltage minimum and post-reset recovery, measures self-induced events, and supports adjustment of induced events based on observed waveforms. |
| [`filter_traces.py`](FaultMeasureStation/filter_traces.py) | Classifies trials, generates statistics and plots, and exports filtered CSV files while preserving alignment between ADC buffers and DSO channels. |

### Oscilloscope Signals

| Channel | Signal and Purpose |
| --- | --- |
| **CH1** | Monitored voltage signal: local glitch minimum and post-reset recovery. |
| **CH2** | Victim AES activity signal: a rapid falling transition indicates normal completion, whereas a slow falling transition is consistent with a reset in the measurement circuit used. This channel is also the default DSO trigger source. |
| **CH3** | Attack circuit pulse: identifies the timing of the induced glitch. |

The CH3 high level may settle at approximately **1 V** due to the characteristics of the physical setup. The analysis scripts use configurable thresholds and hysteresis to prevent noise from splitting a single pulse into multiple detected segments.

### Installation and Acquisition

Use STM32CubeIDE with the three firmware projects provided in the repository. The measurement station requires Python, the dependencies listed in the repository, and a VISA backend compatible with the DSO.

From the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r FaultMeasureStation/requirements.txt
cd FaultMeasureStation
```

**Self-induced** acquisition, without arming the attacker:

```bash
python3 acquire.py --protocol 1 \
  -b BODYGUARD_PORT --scope \
  --repeat 100 --auto-save --no-plot \
  --out-dir acquisizioni/B1/K1V1
```

**Induced** acquisition, using all three boards:

```bash
python3 acquire.py --protocol 2 \
  -b BODYGUARD_PORT -v VICTIM_PORT -a ATTACKER_PORT \
  --scope --repeat 100 --auto-save --no-plot \
  --out-dir acquisizioni/B1/K1V1
```

Replace the port placeholders with those of the experimental setup. `--scope` uses the default VISA resource defined in the script; `--scope VISA_RESOURCE` specifies an alternative resource. The configured serial rates are **209700 baud** for Bodyguard and **115200 baud** for both F4 boards.

The script creates the `Autoinduced_Traces` and `Induced_Traces` subdirectories. In the organized dataset, these event types are stored under `Autoinduced` and `Induced`.

Trials affected by buffer conversion errors or handled acquisition acknowledgment (ACK) timeouts are repeated without incrementing the counter. Saving requires a valid DSO acquisition: `--repeat 100` alone does not guarantee 100 usable traces after filtering. Verify the final count in the reports and acquire additional trials as needed.

See [CHARACTERIZATION.md](FaultMeasureStation/CHARACTERIZATION.md) for characterization modes and parameters.

### Filtering and Export

For **self-induced** events, the filter searches for a slow falling transition on CH2 consistent with a reset. A rapid falling transition, characteristic of the square-wave signal at the end of AES execution, identifies a trial to be discarded.

For **induced** events, temporal ordering is checked in addition to the reset criterion:

1. The onset of the final CH2 falling transition, at 90% of the signal amplitude, is used to estimate the reset time.
2. The CH3 rising edge identifies the glitch.
3. A glitch occurring after the estimated reset time leads to rejection; temporally close or ambiguous cases require review.

Temporal precedence is a criterion for experimental consistency; it does not, by itself, establish that the glitch caused the reset.

```bash
python3 filter_traces.py Dataset/B1/K1V1/Autoinduced \
  --mode auto --max-good 100 --plots -1

python3 filter_traces.py Dataset/B1/K1V1/Induced \
  --mode induced --max-good 100 --plots -1
```

The filter generates `report.html`, JSON statistics, CSV results, and plots. It excludes rows labeled `discard` and requests confirmation for `review` rows considered for export. The `filtered/` subdirectory contains CSV copies with matching Run IDs across all available channels and buffers; the original files remain unchanged.

`--max-good 100` limits the selection to 100 trials, including accepted review cases. If fewer eligible trials are available, only those trials are exported. The complete parameter definitions and filtering rules are provided in [FILTER_TRACES.md](FaultMeasureStation/FILTER_TRACES.md).

## Dataset

The dataset is organized by **victim board**, **key–plaintext pair**, **voltage level**, and **event type**. The target sample size is **100 traces per event type**, induced and self-induced, for each acquired experimental condition. Raw acquisitions may include additional trials that are subsequently excluded during filtering.

Reference directory structure:

```text
FaultMeasureStation/Dataset/
└── B1/
    ├── Characterization/
    └── K1V1/
        ├── Autoinduced/
        └── Induced/
            ├── bodyguard_adc1.csv
            ├── bodyguard_adc2.csv
            ├── scope_ch1.csv
            ├── scope_ch2.csv
            ├── scope_ch3.csv
            └── filter_reports/
```

Each acquisition row begins with a **Run ID** shared by the files belonging to the same trial. In the DSO CSV files, the first row, identified by `TIME`, contains the time axis in seconds; sample values are expressed in volts. Bodyguard CSV files contain raw ADC codes.

The files `scope_ch1.csv`, `scope_ch2.csv`, and `scope_ch3.csv` are excluded from version control through `.gitignore`: they may be present in a local dataset copy without being included in a Git clone. DSO-based filtering also requires these files.

## Experimental Design

Acquisitions follow the design presented in the tables below. The identifiers denote:

- **B1–B6:** six physically distinct STM32F4 victim boards.
- **K1–K3:** the three key–plaintext pairs selectable in the AES workload.
- **V1–V3:** three minimum-voltage levels defined relative to the characterized self-induced minimum: **V1 = self-induced Vmin**, **V2 = 0.90 × self-induced Vmin**, **V3 = 0.80 × self-induced Vmin**.
- **S1–S3:** measurement sessions to which the board–K–V combinations are assigned.

The percentages refer to **Vmin**, rather than the nominal supply voltage. The self-induced reference is characterized on the experimental setup and used to adjust the circuit for induced-event measurements.
